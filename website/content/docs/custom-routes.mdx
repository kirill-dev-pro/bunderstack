# Custom routes

Some endpoints don't fit generated CRUD or tRPC — a webhook a third party POSTs
to, an OAuth callback, a public REST route. Declare them with `routes`:

```ts
import { Hono } from 'hono'

const app = await createBunderstack({
  schema,
  access,
  routes: (ctx) => {
    const r = new Hono()

    r.post('/webhooks/telegram', async (c) => {
      const raw = await c.req.text()
      if (c.req.header('x-telegram-bot-api-secret-token') !== ctx.env.TELEGRAM_WEBHOOK_SECRET) {
        return c.json({ error: 'unauthorized' }, 401)
      }
      await ctx.jobs.enqueue('processTelegramMessage', { raw })
      return c.json({ ok: true })
    })

    return r
  },
})
```

You get a real Hono app — bunderstack only mounts it.

## Why a callback

Routes declared in a separate file cannot `import { app }`, because `app` is the
value being constructed. The callback receives the context instead, which is the
same reason `trpc` and `jobs` take builders.

For separate files, annotate the parameter:

```ts
// src/routes/telegram.ts
import type { BunderstackRouteContext } from 'bunderstack'
import { Hono } from 'hono'

import type * as schema from '../schema'

export function createTelegramRoutes(
  ctx: BunderstackRouteContext<typeof schema, Env>,
): Hono {
  const r = new Hono()
  r.post('/webhooks/telegram', async (c) => { /* … */ })
  return r
}
```

## The context

| Member | What it is |
| --- | --- |
| `db` | Your Drizzle client, typed from `schema` |
| `env` | Validated environment, typed from your `env` config |
| `storage` | Storage facade |
| `email` | Email facade |
| `jobs` | `enqueue()` and `tick()` |
| `realtime` | `publish()` |
| `auth` | The BetterAuth instance |
| `getSession(request)` | `{ user, activeOrganizationId }` |
| `getUser(request)` | `AccessUser \| null` |

Session resolution is **lazy**. A webhook has no session, and resolving one
eagerly would spend an auth round-trip on every request for a value nobody
reads. Call it only when the route needs it:

```ts
r.get('/api/reports/summary', async (c) => {
  const { user } = await ctx.getSession(c.req.raw)
  if (!user) return c.json({ error: 'unauthorized' }, 401)
  return c.json(await buildSummary(ctx.db, user.id))
})
```

Custom routes are **public by default** — bunderstack applies no implicit
authentication, because the common case has no session.

## Mounting and precedence

The returned app is mounted at `/` **before** bunderstack's own routes, so a
custom route can sit in front of the core app. `app.handler` remains the single
entry point.

Because they are mounted inside, custom routes are covered by your `rateLimit`
configuration automatically.

The raw request body is untouched by anything upstream, so `c.req.text()`,
`c.req.arrayBuffer()`, and `c.req.raw` all work for HMAC signature
verification.

## Reserved paths

A route that shadowed `/api/auth/*` would break authentication silently, so
collisions throw at startup instead:

```
[bunderstack] routes: 1 route(s) collide with bunderstack's own:
  GET /api/posts — it collides with the generated CRUD route for table "posts"
Choose different paths.
```

Reserved: `/health`, `/api/health`, `/api/realtime`, and the prefixes
`/api/auth/`, `/api/trpc/`, `/api/files/`, `/files/`, plus `/api/<tableName>`
for every access-enabled table. A parameter or wildcard as the first segment
under `/api/` is also rejected — it would shadow every CRUD route at once.

A table that is not access-enabled has no CRUD route and therefore does not
collide. Enabling it later turns a working custom route into a startup error,
which is the intended trade: a loud failure rather than a silent one.

## Errors

A custom route that throws produces Hono's default 500. Bunderstack installs no
error handler over your routes, so your own `r.onError(...)` is not shadowed.

Custom routes stay outside the typed client surface — they are an escape hatch,
not part of the inferred contract.
