# Почему этот код — правильная форма для Solid 2

Разбор архитектуры `examples/todo-solid-native` и бэкенд-контракта
`GET /api/{table}/live` (ветка `feat/solid-native-backend`).

## 1. Отправная точка: три свойства рантайма Solid 2

Все решения примера выводятся из трёх фактов о работе Solid 2.

**1.1. Реактивность — это граф чтений, а не компонент.**
Единица обновления — конкретное свойство конкретного узла. `checked={todo.done}`
создаёт одну подписку на одно свойство одного прокси; клик по чекбоксу меняет
ровно один атрибут в DOM и один класс в `class={{ done: todo.done }}`
(объектная форма классов из 2.0 компилируется в прямые операции с
`element.classList`). Цена обновления UI пропорциональна числу изменившихся
полей, а не числу строк в списке.

**1.2. Асинхронность живёт в вычислениях.**
Промис из `createMemo` или проекционного стора — «незасеттлившееся чтение»:
до первого значения оно сообщает о неготовности (`NotReadyError` → `<Loading>`),
при отказе ошибка идёт по графу в `<Errored>`. Чтения — то, что оседает.

**1.3. Записи батчатся микрофлашем; транзакции — только через `yield`.**
Записи видимы после сброса очереди микротасков; всплеск коммитится одним
обновлением. Транзакционная семантика (атомарные группы, автооткат) существует
только внутри `action(function* ...)`.

Практический вывод из 1.3, проверенный по исходникам
`@solidjs/signals@2.0.0-rc.0`: метки `affects()` вне экшена снимаются в конце
обычного флеша — раньше, чем завершится любой сетевой `await`. Поэтому
«pending на время запроса» без экшена построить нельзя, а экшен оправдан только
там, где есть записи *после* await.

## 2. Главный принцип: данные движутся ровно один раз

    INSERT/UPDATE в БД
      -> publish (broadcast-on-write)
        -> SSE-кадр {type:'upsert'|'remove', record}
          -> applyFrame(): одна мутация локального массива
            -> setItems(): запись в стор
              -> flush: обновлены только затронутые свойства строк

Ни на одном шаге нет второй копии состояния:

- **Нет кэша отдельно от рендера.** У TanStack Query источник истинности —
  кэш обсерверов, который затем копируется в слой рендера; здесь стор и есть
  единственный источник, `<For>` читает его напрямую.
- **Нет инвалидации.** Цикл «изменение -> пометить устаревшим -> рефетч ->
  дифф» заменён адресной доставкой: сервер уже решил, что кадр относится к
  этому view, поэтому кадр превращается в O(1)-мутацию массива.
- **Нет повторного чтения после записи.** Мутация патчит UI сама лишь
  оптимистично; эхо приходит тем же стримом, что и чужие правки.

## 3. Как каждый элемент кода использует Solid 2

### 3.1. `<For>` + стор: идентичность строк переживает кадры

`<For>` в Solid 2 по умолчанию ключуется по идентичности объектов и пере-
использует ранее отображённое значение для неизменившихся элементов. Строки
попадают в стор через `applyFrame`, который сохраняет объекты неизменившихся
строк как есть — значит, при кадре `upsert` для одной задачи DOM остальных
строк не трогается вовсе, а у изменённой обновляется только `checked`/класс.

Это точка стыковки с бэкендом: контракт «снапшот + upsert/remove» спроектирован
именно под keyed-рендер Solid. Кадр несёт полную запись (не дифф полей), потому
что reconcile по ключу в любом случае сводит его к точечным правкам.

### 3.2. Стор с черновыми сеттерами вместо ручных сигналов на каждую строку

Один `createStore<Todo[]>([])` хранит весь список глубоко-реактивно: чтение
`todo.done` подписывается только на это поле этой строки. Черновые записи
(`setItems(draft => { ... })`) дают мутабельный стиль без `produce` —
оптимистичный тоггл это три строки:

```ts
todos.patch((draftTodos) => {
  const current = draftTodos.find((item) => item.id === todo.id)
  if (current) current.done = done
})
```

Сравните с моделью «сигнал на ресурс»: отдельные флаги pending/error на каждый
запрос, ручная синхронизация кэша, ключи запросов. Здесь состояние данных —
один массив, а его жизненный цикл описан ниже.

### 3.3. Слои состояния по времени жизни — буквально по документации

Доки Solid 2 предписывают разделять состояние по lifetime. В примере ровно три
слоя, каждому — свой носитель:

| Слой | Носитель | Почему |
|------|----------|--------|
| Постоянные данные (строки) | `createStore`, пишет стрим | живёт вечно, меняется точечно |
| Процессное состояние канала (`connected`, `ready`, `error`) | `createSignal` внутри `createRoot` | ортогонально данным; читается напрямую в JSX |
| Эфемерные заметки (`failure`) | `createSignal` | должно переживать откат оптимистики |

### 3.4. `createRoot` + `onCleanup`: владение вне компонентного дерева

Стрим-цикл не является чтением, ему нужен owner для диспоза.
`createTodoStore()` оборачивает всё в `createRoot` — дочерний корень компонента
уничтожается вместе с ним (в 2.0 `createRoot` принадлежит родителю по
умолчанию), а `onCleanup` внутри связывает остановку цикла и `AbortController`
с жизнью владельца. Это канонический способ держать реактивное состояние в
фабрике, а не в модуле (модульный синглтон ломал бы SSR и тесты).

### 3.5. `untrack` на записях из императивного контекста

Стрим-цикл пишет в сигналы из асинхронного продолжения. Оборачивание в
`untrack(() => setConnected(true) /* ... */)` — не косметика: оно явно
декларирует «это запись, не зависимость» и снимает дев-диагностики Solid 2
(«write under owned scope», случайные зависимости вычислений).

### 3.6. Мутации — простые async-функции: честное применение критерия экшенов

Документированный критерий: *action нужен, только если записи происходят после
await*. Наши мутации пишут оптимистично до fetch и ничего не пишут после —
правду приносит стрим. Поэтому генераторы были бы церемонией без семантики:

- откат при отказе нам не нужен — отказ ловит один глобальный слушатель
  `unhandledrejection`, который показывает notice и вызывает `resync()`
  (реконнект = свежий снапшот = авторитетная правда);
- двойной сабмит блокируется синхронной очисткой draft до первого await —
  второй клик видит пустой инпут. Никаких in-flight флагов;
- fetch-отказы никогда не попадают в реактивный граф, поэтому гонять их через
  `<Errored>` было бы неправильно: граница зарезервирована для того, что
  действительно через граф течёт.

### 3.7. `clientOnly`: CSR для данных, SSR для оболочки

Приложение рендерит оболочку на сервере и монтирует список в браузере:
стриму нужен браузерный origin, а гидрация данных потребовала бы
`ssrSource`-танцев. `clientOnly` — штатный примитив именно для этого.

## 4. Чего мы сознательно НЕ делаем — и почему это тоже использование Solid 2

**Проекционный стор с бесконечным генератором.** Красивая идея
`createStore(async function* () {...}, [], { key: 'id' })` разбивается о
семантику: проекция тянет iterable один раз — это чтение, ждущее первого
значения, а не подписка. Проверено минимальным репро и подтверждено исходниками.
Отсюда императивный цикл в `createTodoStore` — не капитуляция, а правильный
носитель: бесконечный поток не оседает, значит ему не место в графе чтений.

**`<Loading>`/`<Errored>` вокруг списка.** Границы отвечают на вопрос «когда
оседет чтение». Живой вид не оседает никогда; момент появления первого
снапшота — это `ready`, обрыв — это `error`. Сигналы здесь точнее границ.

**`action`/`affects`/`isPending`.** Единственный выигрыш — дизейбл кнопки на
время запроса. Цена: генераторы, транзакционная обвязка и знание того, что
`affects` не работает вне транзакции. Синхронная очистка draft дешевле всех
трёх.

**Оптимистичные оверлеи с автореverted.** `createOptimisticStore` откатывает
записи при отказе экшена. У нас откат достигается `resync()` — одним
реконнектом, который в любом случае нужен при расхождении. Одна механика
вместо двух.

## 5. Что это даёт измеримо

- Весь data layer: ~200 строк вместе с тестами, ноль runtime-зависимостей.
- Запись одной строки: один SSE-кадр → одна мутация массива → одна правка DOM.
  Ни одного рефетча, ни одного лишнего рендера чужих строк.
- Реконнект: одна HTTP-команда, восстановление встроено в сам протокол
  (снапшот на каждом соединении). Нет клиентских буферов событий,
  Last-Event-ID-бухгалтерии и ветки «пересинхронизация после пропуска».
- Ошибки: два пути (граф для чтений/рендера, глобальный слушатель для
  императивных отказов), оба по одному месту.

## 6. Формула

Solid 2 даёт fine-grained граф для **оседающих** состояний и честно не даёт
транзакций вне `yield`-экшенов и подписок из вычислений. Этот код отдаёт графу
ровно то, что оседает (строки данных и их поля), ведёт нескончаемое
(поток кадров) императивно там, где у графа нет семантики, и соединяет их
односторонней трубой «кадр → мутация стора». Каждый примитив — `<For>`,
стор с черновиками, слои сигналов, `createRoot`/`onCleanup`, `untrack`,
`clientOnly` — использован по прямому назначению из документации 2.0, а все
отступления от «идеально реактивного» вида обоснованы проверяемыми фактами о
рантайме, а не удобством.
