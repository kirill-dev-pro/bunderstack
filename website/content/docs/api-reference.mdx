# API Reference

## createBunderstack(options)

```ts
async function createBunderstack<
  TSchema extends Record<string, unknown>,
  const TAccess extends Record<string, TableAccessInput> | undefined =
    undefined,
  const TStorage extends StorageConfigInput | undefined = undefined,
  const TEnv extends EnvConfigInput | undefined = undefined,
  TRouter extends AnyRouter = AnyRouter,
>(
  options: BunderstackConfig<TSchema, TAccess, TStorage, TEnv> & {
    trpc: (t: BunderstackTRPC<TSchema, ValidatedEnv<TEnv>>) => TRouter
  },
): Promise<
  BunderstackApp<TSchema, TAccess, BucketNamesOf<TStorage>, TEnv, TRouter>
>
```

Also accepts `trpc?: AnyRouter` (prebuilt router) or no `trpc` key at all.
Generics are captured so clients can infer tables, buckets, and the tRPC
router from `typeof app` (see `$inferClient` below).

`createBunderstack` is `async`. Select a database integration with a static
subpath import, install only that adapter's optional peer, and then await app
creation:

```ts
import { createBunderstack } from 'bunderstack'
import { libsql } from 'bunderstack/database/libsql'

export const app = await createBunderstack({
  schema,
  database: { adapter: libsql(), url: 'file:./data.db' },
})
```

### BunderstackConfig

```ts
type BunderstackConfig<TSchema, TAccess, TStorage, TEnv> = {
  schema: TSchema
  access?: TAccess // Record<tableKey, TableAccessInput>
  database: {
    adapter: DatabaseAdapter
    url?: string
    authToken?: string
    migrations?: string
  }
  auth?: BetterAuthConfig // native BetterAuth options (except database)
  storage?: TStorage // StorageConfigInput: backends, defaultBucket, buckets
  email?: EmailConfigInput // { from: string; provider?: 'resend' | 'console' | adapter }
  env?: TEnv // EnvConfigInput: server + client Zod schemas
  // trpc is declared on createBunderstack's overloads for contextual typing
  rateLimit?: boolean | RateLimitConfig
  idempotency?: boolean | IdempotencyConfig
  realtime?:
    | boolean
    | {
        keepaliveMs?: number
        bufferSize?: number
        redis?: string | { url: string; token?: string }
      }
}
```

### BunderstackApp

```ts
type BunderstackApp<TSchema, TAccess, TBuckets, TEnv, TRouter> = {
  handler: (req: Request) => Promise<Response>
  // Typed for your schema's dialect: LibSQLDatabase for sqliteTable,
  // PgDatabase for pgTable (see Database dialect below)
  db: DbFor<TSchema>
  auth: Auth
  storage: StorageFacade
  router: Hono
  /** Validated env: base vars + config's `env` extension, fully typed. */
  env: ValidatedEnv<TEnv>
  /** Email facade — always present; send() throws if email isn't configured. */
  email: EmailFacade
  /** Typed custom row publication and selected runtime transport. */
  realtime: RealtimeFacade<TSchema>
  startWorker(options?: AppStartWorkerOptions): Promise<WorkerHandle>
  runWorker(options?: AppRunWorkerOptions): Promise<void>
  /** Deploy-time description, including realtimeTransport. */
  manifest: BunderstackManifest
  /** Raw tRPC router when the config declared one — escape hatch. */
  trpcRouter?: AnyRouter
  /** Closes real database clients and other app-owned resources. */
  close(): Promise<void>
  /** Type-only carrier for client inference — never assigned at runtime. */
  readonly $inferClient?: {
    schema: TSchema
    access: TAccess
    buckets: TBuckets
    trpc: TRouter
  }
}
```

Export `type App = typeof app` and the client packages infer everything from
it.

## Database adapters

The schema selects its dialect (`sqliteTable` → SQLite; `pgTable` → Postgres),
while `database.adapter` selects the client. The adapter dialect must match the
schema and its URL:

| Subpath                            | Factory        | Optional peer                 | URL                      |
| ---------------------------------- | -------------- | ----------------------------- | ------------------------ |
| `bunderstack/database/libsql`      | `libsql()`     | `@libsql/client`              | `file:…` or `libsql://…` |
| `bunderstack/database/pglite`      | `pglite()`     | `@electric-sql/pglite`        | `file:…` or `memory://`  |
| `bunderstack/database/bun-sql`     | `bunSql()`     | none (Bun provides `Bun.sql`) | `postgres://…`           |
| `bunderstack/database/postgres-js` | `postgresJs()` | `postgres`                    | `postgres://…`           |

Install only the selected optional peer. `drizzle-orm`, `better-auth`, Hono,
and Zod are required peers because the root entrypoint uses them. Drivers,
Nodemailer, drizzle-kit, and TypeScript are optional peers; TypeScript remains
`>=5` because the package publishes `.ts` source, while optional peer metadata
does not force it into Bun installations that already transpile that source.

With `BUNDERSTACK_INTROSPECT=1`, the selected adapter returns
`drizzle.mock({ schema })` and does not create a database connection. Real
libSQL, PGlite, postgres.js, and Bun SQL clients are app-owned and closed by
`await app.close()`.

**Import Drizzle builders and operators directly from `drizzle-orm`** —
`sqliteTable`/`pgTable`/`eq`/`desc`/`sql`/etc. are not re-exported from
`bunderstack`. Two dialect-specific subpaths remain for the pieces that must
be static per dialect: `bunderstack/schema` (sqlite) / `bunderstack/schema/pg`
(Postgres) export the internal file-meta/idempotency tables; `bunderstack/typeid`
(sqlite) / `bunderstack/typeid/pg` (Postgres) export the `typeid()` column
builder.

## bunderstack/provision

```ts
function provision(app: object, options?: { force?: boolean }): Promise<void>
```

Optional entry point — import it only if you want Bunderstack to manage the
database on boot. When `<migrations>/meta/_journal.json` exists (folder set by
`database.migrations`, default `./migrations`), applies pending migrations via
drizzle-orm's migrator. Otherwise pushes the schema via drizzle-kit (dev-only
dependency; `bun add -d drizzle-kit`). `force` allows a push that would drop
data. The low-level `provisionSchema(db, schema, options?)` (push only) is
exported from the same entry.

**Postgres + `Bun.sql` + dev push:** drizzle-kit's schema push does not yet
support the `Bun.sql` driver (it assumes raw query results carry a `.rows`
property, which `Bun.sql` doesn't provide) — this affects only the no-migrations
dev-push path, not committed migrations. If you hit it, generate and commit
migrations (`bunx drizzle-kit generate`) instead of relying on push, or run
against Postgres via `postgres.js` (Node) during development.

## Client packages

### bunderstack-query

```ts
function createClient<TApp extends AnyBunderstackApp>(options?: {
  baseUrl?: string // default '/api'
  fetch?: (input, init?) => Promise<Response>
  queryClient?: QueryClient // enables mutation cache invalidation
}): BunderstackClient<TApp>
```

Lazy proxy: `api.<table>` (list/get/create/update/delete + TanStack Query
option factories) and `api.files.<bucket>` (upload/url/delete). Also exports
`MAX_LIST_LIMIT` (200 — the server's per-request list cap), `InferSelect`,
`InferInsert`, and the explicit `createBunderstackQueryClient` builder.

For a client that also exposes the typed `api.trpc` proxy, use the optional
entrypoint:

```ts
import { createTRPCClient } from 'bunderstack-query/trpc'

const api = createTRPCClient<App>({ queryClient })
```

### bunderstack-sync

```ts
function createSyncClient<TApp extends AnyBunderstackApp>(options: {
  queryClient: QueryClient
  baseUrl?: string
  fetch?: (input, init?) => Promise<Response>
  realtime?: boolean // default: true in the browser, false during SSR
}): BunderstackSyncClient<TApp>
```

Per table: `collection`, `table`, `scopedCollection(options)`,
`collectionByIds(ids)`; plus `files.<bucket>` and `realtime` — see
[Sync Collections](/docs/sync-collections).

## RealtimeFacade

```ts
type RealtimeTransport = 'disabled' | 'memory' | 'redis'

interface RealtimeFacade<TSchema> {
  readonly enabled: boolean
  readonly transport: RealtimeTransport

  publish<TTable extends SchemaTable<TSchema>>(
    table: TTable,
    action: RealtimeAction,
    record: InferSelectModel<TTable>,
  ): Promise<void>
}
```

Exposed as `app.realtime` and `ctx.realtime` (in tRPC, jobs, and cron). Used to publish custom write operations to clients subscribed to realtime tables.

- `publish(table, action, record)`: Takes a Drizzle `table` object (which guarantees the physical table exists in `schema`), an `action` string (like `'create' | 'update' | 'delete'`), and the full `record` (which TypeScript constrains to the table's `InferSelectModel`).
- `transport`: The active runtime transport: `'disabled'`, process-local
  `'memory'`, or shared `'redis'`.

If server realtime is disabled or no broker is available, `realtime.enabled` is `false` and `publish` is a no-op. Publishing is async and fire-and-forget: failure to publish into Redis does not crash the caller.

## Worker realtime safety

```ts
type AppRunWorkerOptions = AppStartWorkerOptions & {
  allowProcessLocalRealtime?: boolean
}
```

`app.runWorker()` is for a standalone worker process. Since 0.9.0 it rejects
`realtime.transport === 'memory'`, because publications from that broker cannot
reach SSE clients connected to a separate web process. Configure `REDIS_URL` or
`realtime.redis`, embed the worker with `app.startWorker()`, or set
`allowProcessLocalRealtime: true` only when jobs never publish realtime events.

`app.manifest.realtimeTransport` exposes the configured transport as
`'disabled' | 'memory' | 'redis'` for deploy tooling.
